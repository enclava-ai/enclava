<objective>Add recovery, stale-lock handling, retention policy, admin metrics, and operational docs while staying within the existing in-process scheduler/runtime architecture.</objective>

<threat_model>
<threat severity="high" id="T-08-01">A crashed worker could leave workflow runs stuck in `running` forever, hiding failures and blocking operators from retrying.</threat>
<mitigation>Add stale lock recovery that finds expired `running` runs, marks them failed with a recovery reason, clears lock metadata, appends a run event, and records audit metadata. Do not requeue them because current runtime does not resume safely from arbitrary completed step checkpoints.</mitigation>
<threat severity="high" id="T-08-02">Automatic stale recovery could duplicate side-effecting work if it re-runs a partially completed workflow.</threat>
<mitigation>Conservative recovery marks expired locked runs failed and requires normal retry behavior to create a new run. The recovery path must not invoke `execute_run` or create a replacement run automatically.</mitigation>
<threat severity="medium" id="T-08-03">Retention cleanup could remove durable auditability or immutable workflow history.</threat>
<mitigation>Retention applies only to verbose workflow events and artifact payload/rows according to explicit policy. It must not delete workflow definitions, versions, runs, step runs, approvals, or audit logs. Provide dry-run counts before destructive cleanup.</mitigation>
<threat severity="medium" id="T-08-04">Operational metrics could leak cross-tenant workflow information to normal users.</threat>
<mitigation>Admin metrics, retention, and recovery endpoints require admin/superuser or `workflow.manage`. The regular operations list remains scoped to visible workflows.</mitigation>
</threat_model>
