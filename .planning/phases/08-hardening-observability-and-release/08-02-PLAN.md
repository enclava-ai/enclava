<objective>Add release coverage for workflow backend behavior, frontend workflow surface wiring, and Nightly RAG Summary UAT without changing workflow product behavior.</objective>

<threat_model>
<threat severity="high" id="T-08-02-01">Release criteria could appear covered while core workflow failure modes remain untested, allowing regressions in scheduling, retry, redaction, or immutable version history.</threat>
<mitigation>Add focused backend and UAT tests that exercise the exact release criteria rather than only importing existing unit tests. The tests must assert state transitions, idempotency, retry lineage, artifact/redaction behavior, and version references.</mitigation>
<threat severity="medium" id="T-08-02-02">Adding a full frontend test framework late in the milestone could produce a brittle, half-configured harness that does not run in CI or local verification.</threat>
<mitigation>Use an executable Node-based workflow surface guard that checks route, proxy, API client, builder, operations console, schedule board, run detail, and artifact preview wiring with no new dependencies. Document this as a release guard, not a substitute for future component/E2E testing.</mitigation>
<threat severity="medium" id="T-08-02-03">UAT tests could rely on external model, RAG, or browser services and become flaky or impossible to run in test containers.</threat>
<mitigation>Keep automated UAT deterministic inside the backend test container using local database state and service fakes. Keep browser/operator smoke checks in docs and live smoke verification.</mitigation>
<threat severity="medium" id="T-08-02-04">Release documentation could drift from the runnable checks and mislead operators.</threat>
<mitigation>Write `docs/workflows/uat.md` with exact commands and explicit mapping from WF-TEST/WF-REL criteria to automated tests, frontend guard checks, and live smoke checks.</mitigation>
</threat_model>
