<objective>Add minimal API/event trigger foundations with authenticated fire endpoints, required idempotency semantics, queued run creation, and compact builder/docs surface.</objective>

<threat_model>
<threat severity="high" id="T-07-08">An unauthenticated or unauthorized caller could fire workflows and execute sensitive downstream steps.</threat>
<mitigation>Expose trigger fire only through authenticated internal API routes. Require workflow ownership/admin, `workflow.manage`, or `workflow.trigger` permission to fire matching API/event triggers.</mitigation>
<threat severity="high" id="T-07-09">Retries from API/event producers could create duplicate workflow runs.</threat>
<mitigation>Require a caller-supplied `idempotency_key` and store derived per-trigger run idempotency keys like `api:{trigger_id}:{key}` and `event:{trigger_id}:{key}`. Existing runs return duplicate metadata instead of creating another run.</mitigation>
<threat severity="medium" id="T-07-10">API/event trigger support could accidentally become a public webhook or event-bus scope expansion.</threat>
<mitigation>Keep this release to authenticated internal fire endpoints and service methods. Do not add public webhook secrets, outbound calls, event subscription adapters, retries from external brokers, or background trigger consumers.</mitigation>
<threat severity="medium" id="T-07-11">Ambiguous trigger names could make operators fire the wrong workflow.</threat>
<mitigation>Validate API slugs and event names with explicit formats and return a per-trigger result list containing workflow id, trigger id, run id, and duplicate/skipped status.</mitigation>
</threat_model>
