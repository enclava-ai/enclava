<objective>Add approval request steps that pause workflow runs, allow authorized approval or rejection, resume deterministically after approval, and show the full decision trail in run detail.</objective>

<threat_model>
<threat severity="high" id="T-07-04">An unauthorized user could approve a workflow run and cause sensitive or destructive downstream steps to execute.</threat>
<mitigation>Add an explicit approval authorization gate in runtime actions. Allow only admins, workflow owners, actors with `workflow.manage`, actors with `workflow.approve`, or users listed in the approval step config.</mitigation>
<threat severity="high" id="T-07-05">A resumed paused run could re-execute earlier steps, duplicate external work, or lose prior outputs.</threat>
<mitigation>Persist pause metadata with the approval id, approval step key, next step index, and prior outputs. Resume from the next ordered step only, rebuilding the runtime context from persisted outputs.</mitigation>
<threat severity="medium" id="T-07-06">A rejected approval could look like a technical failure or silently stop a run without operator context.</threat>
<mitigation>Persist the approval status, resolution comment, resolver, skipped remaining step rows, `approval_rejected`, `run_skipped`, and audit events. Surface the pending/resolved approval in run detail.</mitigation>
<threat severity="medium" id="T-07-07">Approval prompt content could leak sensitive prior outputs through events or notifications.</threat>
<mitigation>Render approval title/body through existing template context but store them under the run redaction policy and keep events limited to approval ids, step keys, status, and resolver metadata.</mitigation>
</threat_model>
